# THPS2 recomp: ROM versions and code classes

How the THPS2 host runs both releases of Tony Hawk's Pro Skater 2 (USA and Europe) from one binary without
`if (version == ...)` code. The design is the one of the THPS1 port: a **version** is a ROM we recognise (a row of
`decomp/common/games.toml`), a **code class** is a set of recompiled functions (one generated payload), and the host reads
**names** from a generated table (`thps::sym()`) and **facts** from `thps::version()`. A difference in behaviour becomes a named
field in those tables, never a version test in C++. Facts only here: hashes, addresses, names.

## What differs between the releases

| | USA | Europe |
|---|---|---|
| Header | `THPS2`, NTQE, rev 0 | `THPS2`, NTQP, rev 0 |
| SHA-1 | `458ac754...` | `803672c1...` |
| XXH3-64 | `8E5ABB6C1CE403DB` | `F32FEE0FC9FE5F6A` |
| Main image | `0xE7E10` bytes, `GameEntry` `0x800B6AF8` | `0xE7ED0` bytes (+`0xC0`), `GameEntry` `0x800B6B28` |
| Code class | `us` | `eu`: a re-link, shifts of `0x20` to `0xC0`, 6 functions differ, 8 of 16 overlays differ beyond relocation |
| Overlay table | `0x800EB2F0`, tail from `0xF587B6` | `0x800EB3B0`, tail from `0xF587F8` |
| `tv_default` | `ntsc` | `ntsc` (PAL releases run at NTSC timing; `--tv pal` is experimental) |
| Status | supported | supported |

The stored copies of the dumps are `thps2.n64.us.z64` and `thps2.n64.eu.z64` (the `game_id` of the rows).

**TV type.** Europe's TV-type accessor returns "is PAL" where USA's returns "is not PAL" (as in THPS1's Europe). Its two live
callers, in `func_80037350`, set two flags; the third caller, a black-screen lockout, is dead code in both builds. At NTSC timing,
Europe takes the branch USA takes on a PAL console at those two sites; nothing else changes. The region check
(`Tv_IsHomeRegion`) is bypassed by a hook, see [recomp.md](recomp.md#4-the-rest-of-the-host).

## What THPS2 adds to the version scheme

- **Front-end overlays per class.** The 16 relocatable screens ([overlays.md](overlays.md)) are linked against the main image, so every
  code class has its own. `decomp/common/overlay_recomp.py` pre-links the class's 16 blobs and appends them to the class's code blob
  (`build/gen/<class>/thps2.host.blob.bin`), and writes the class's table `versions/<class>/overlay_table.inc` (names, ROM offsets,
  sizes, blob offsets: numbers only, committed). `src/payload.cpp.in` puts that table into the class's `thps::Payload`;
  `src/hooks.cpp` maps a screen when the game's loader DMAs it, from the active payload's table. Registration is librecomp's, once per
  process, with the section count passed as the total as well.
- **The generator is shared.** `decomp/common/gen_versions.py` serves THPS1, THPS2 and THPS3 with a per-game profile (`game/game.toml`);
  `tools/gen_versions.py` is THPS2's thin wrapper, and its N64Recomp input is the overlay-appended blob.

## Names inside overlays

A hook target inside an overlay (Skip Intro's `Ovl_IntroUpdate`) is named per class in
`versions/<class>/host_force.toml` `[overlay_force]` as `"t2_intro+0x114" = "Ovl_IntroUpdate"`; `overlay_recomp.py --force` names it and
fails if the offset is not a function start.

## How the Europe class was made (and how the next one would be)

1. Probe: hashes, `thps_unpack.py --game thps2_eu` (15 of 15 chunk CRCs, the `main_sha1`), `sigmatch.py` and an aligned masked diff
   against USA, `overlay_table.py` on both. A different `main_size`, `entry` or BSS end means a different link: a new class.
2. A `games.toml` row with the geometry that differs, and a `classes.toml` entry.
3. `tools/seed_class.py eu ROM --src-rom baserom.z64 --src-main baserom.main.bin`: names and exact function ranges from the solved USA
   symbols. THPS2's wrapper also lists every unnamed whole-body match and places the unmatched twins by shift, because the
   plain seeding missed 42 function starts (libmus command handlers reached through a pointer table). Result: 3,354 functions, one
   to one with USA's.
4. `host_force.toml`: the 17 forced names at Europe's addresses, the hidden-start `splits` moved with their function (+`0x30`), the
   coprocessor-2 sites, and `[overlay_force]`.
5. `data_syms.toml`: `tools/translate_data.py eu` (votes through matched pairs) for the data, a string search for the two notice
   texts, and struct offsets checked by counting loads and stores inside matched pairs.
6. `tools/gen.py`, build, `--check-rom`, boot, `tests/run.py --version thps2_eu`.

**What never changes when a version is added:** the shared host sources (`decomp/common/host/src`), `CMakeLists.txt`, the hook blocks, the scenarios.

## The first-run recipes

The downloaded app builds the game from the user's dump (the split build, ADR 0005), one recipe per class in `recomp-host/recipes/<class>/`:

| File | What |
|---|---|
| `thps2.host.syms.toml` | function names, addresses and sizes (the class's symbol file with the host's forced names; the front-end screens are not in it) |
| `blob.txt` | XXH3-64 fingerprint of the code blob (a hash, not data) |
| `overlays.txt` | the 16 front-end screens: names, ROM offsets and sizes of each screen's code and relocation stream, the function map, and a fingerprint of the ROM range they cover |

Overlays make a recipe more than a symbol file, because the overlay blob is part of the generated input. The ROM-free answer is that the first run
reads the screens' bytes and relocation streams from the user's ROM (`decomp/common/firstrun/overlay_rom.cpp`) and the recipe holds only the layout
and the function map; a dump whose screens do not match the fingerprint is refused. `us` serves the USA dump and `eu` the Europe dump; the app picks
the recipe by hash. One zip carries both. `tools/package_split.py --refresh-recipes [--class us|eu]` rewrites them (needs the ROMs).
